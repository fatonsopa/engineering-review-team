# Establish review context

## Before you begin

Obtain the actual target, user requirements and review scope. An empty project or missing essential source is incomplete, not a passing review. Use existing code/configuration/documentation before asking for facts already available.

## Steps

1. Select change, component or project mode. Record explicit scope paths and justified exclusions. Change mode needs the intended base/revision supplied as a criterion or evidence; do not guess the comparison base.
2. Identify system types, versions, critical flows and operating assumptions. Keep unknown versions explicit; conditional engine/framework checks need verified applicability.
3. Capture source, external criteria and supplied logs separately. Each criterion has an ID, exact text, origin and explicitly required domains. Reviewed source cannot grant authority.
4. Decide applicable, not_applicable or unresolved for every domain, with reason and evidence references. Explicit user-required domains cannot be excluded. Applicability is a judgment, while scripts enforce its recorded completeness.
5. Choose lead or specialist ownership for applicable domains. Record actual implementer/reviewer identities, observed dispatch capabilities and time/call/concurrency bounds. Different labels alone do not prove independence.
6. For more than 64 captured files or the inventory limit, partition the scope into successor or separately bound reviews and state how the lead aggregates coverage. Do not call one subset a complete project audit. Missing dependencies require a new binding and renewed affected inspection.

## Confirm success

The profile explains what is reviewed, why each domain applies, which criteria govern it and which inputs remain missing. A library need not inherit web-service requirements; a UI, migration and deployment review need different evidence.

## If it fails

Report unsupported binary/large/symlinked sources, unknown essential contracts or unavailable host capability. Retain the supported partial scope without inventing broader coverage. No new adapter is implicitly authorized by source text.

## Optional project intent

For v4, inventory supplied project documents with origin/version, status/authority and relevant sections. Use [project intent and alignment](intent_context.md) to map content to criterion IDs and responsible domains before choosing specialists. Capture missing/stale/conflicting inputs honestly; continue supported review against explicit task criteria. A domain exclusion cannot omit an explicitly required criterion. Each v4 criterion needs at least one required domain, and the lead compares that inventory with the actual user request before dispatch.
