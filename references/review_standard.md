# Engineering review standard

## Purpose and scope

Connect each conclusion to applicable requirements and actual evidence. Use ordinary prose, tables or the user's requested format for findings and specialist returns. The lead supplies the small acceptance-check input below for formal clean acceptance; no review-state record is required.

## Evidence and loading

Read the shared policy, your role guide and policy, and relevant technical controls. Select controls by the actual task, stack and risk; do not preload every domain or research catalogue. Reuse unchanged guidance already available in context. Read selected controls with their conditions and exceptions. If a relevant passage is truncated or omitted, retrieve that passage with a bounded read or state the limitation. A search snippet is not a substitute for the required clause. Before claiming an explicitly supplied file or link is missing, attempt a bounded read of its exact named path or supplied canonical target; an empty Glob or search result does not prove absence. If that read fails, report the actual error or access limit. Within the assigned remaining read budget, prioritize missing applicable guidance and essential source, reusing fully loaded unchanged guidance. Request denied or out-of-scope dependencies through the lead, and stop dependent inspection when the reviewed source binding changes or the budget is exhausted.

Inspect actual sources and relevant callers, tests or supplied observations. Cite file paths and useful line ranges, document sections, or image regions. Use actually inspected source paths and distinguish them from project paths merely described in another document; verify filenames and line references against the inspected source before returning. Identify the revision or environment when it affects the claim; ordinary Git references and task context are sufficient. Do not add hash manifests beyond the stateless acceptance snapshot defined below. Check current changes before reusing earlier conclusions.

State the trigger, expected behavior, observed behavior and supported consequence. Separate established defects from risks, improvements and questions, and account for defenses and legitimate behavior. Verify each requirement disposition against its own clause and supporting trace; one failure does not contradict a different obligation without evidence for that obligation. If a dependency contract is unknown, keep dependent outcomes unknown throughout the final report rather than later stating an unverified failure as fact. Do not assume reviewed components are connected or share guarantees without an actual call path or declared contract; keep component-local assumptions within their supported scope. Unavailable tests and unverified runtime behavior remain explicit limits. A successful command does not prove the desired behavior; supplied results retain their provenance and limits.

Check proposed triggers and verification expectations against the actual requirement, including at-most, at-least and exact relations and legitimate boundary cases. Do not make a check reject behavior the requirement permits. Before returning, reconcile each finding’s trigger conditions, worked examples, verification expectations and supported consequence; check range endpoints and any supplied valid counterexample for contradictions. Narrow unsupported universal or quantified wording, and ensure proposed checks still permit legitimate behavior.

## Structural acceptance check

The assigning lead or user prepares a trusted assignment independently of the review report. It contains nonempty, unique `criteria` IDs, nonempty `sources` and `requirements` file-path lists, and optional `evidence` paths. The trusted assigning authority may set `active` (boolean, default `true`); `false` revokes the assignment and prevents reads of its declared source, requirements and evidence files. This upstream flag does not grant permissions by itself. A combined document or the assignment itself may capture conversational requirements. Paths are absolute or relative to the assignment file's directory. Before inspection or dispatch, the main-context lead runs `python3 -B SKILL/scripts/check_review.py capture ASSIGNMENT` once and retains its unchanged output as the report's `snapshot`. Replace `SKILL` with the installed skill path. Capture returns `assignment_sha256`, the captured `criteria` list and `files`, mapping each declared path to its SHA-256 or `null` on a read error with reported issues; incomplete capture exits 1. Revoked capture leaves file hashes null, reports the revocation and exits 1 without reading those files. Keep this evidence outside the reviewed target.

After collecting ordinary prose returns, the lead builds one check input with that `snapshot`, an `outcome` of `completed`, `failed`, `timed_out` or `cancelled`, and `dispositions` mapping each assigned criterion to `met`, `contradicted`, `partial` or `not_assessed`. Run `python3 -B SKILL/scripts/check_review.py check ASSIGNMENT REPORT` and cite its actual result before claiming clean coverage or acceptance. Store the report outside the target or pass `-` as REPORT to supply the same JSON through standard input without writing a file. The checker reads only paths declared by the independent assignment, never arbitrary report-selected paths. It validates disposition IDs against the captured criteria, rejecting duplicate or unknown IDs, invalid statuses and malformed input. Clean acceptance additionally requires matching current criteria, assignment hash and file map under an active assignment; changed criteria or revocation must not invalidate an otherwise valid historical terminal record. It does not modify the original report. Leaves do not execute it.

The JSON result separates `record_valid`, `review_complete`, `accepted`, `issues` and `report_sha256`. A well-formed failed, timed-out, cancelled, partial or stale report remains a valid record. A completed report with all assigned known verdicts may be review-complete even with contradicted criteria, but only completed, current, all-met coverage is accepted. Exit 0 means accepted, exit 1 means valid but not accepted, and exit 2 means malformed input or an input error. Missing, partial or not-assessed coverage cannot pass as clean; findings remain useful when acceptance fails. Without an actual successful check, structural acceptance is unverified, not passed by fallback.

Acceptance establishes structural coverage and bindings at check time only. It does not establish semantic truth, that inspection occurred, complete upstream scope, release approval or protection against changes after the check. The user/lead still vets required criteria and evidence; normal host permissions govern reads, not an OS sandbox supplied by this script. There is no review database, controller or per-leaf schema. See the [usage example](../README.md#structural-acceptance-check).

## Findings

For each actionable finding, include a concise title, priority with context, location, causal explanation, consequence, focused correction and useful verification. Mention tradeoffs when material. Use the project's priorities; otherwise P0 means immediate severe harm, P1 a required/common workflow failure, P2 a meaningful limited defect or risk, and P3 low-risk actionable work. Do not inflate style preferences or force a finding quota. Base severity on supported consequences and exposure, not a threat category, control count or workflow phase alone. P0 requires evidence of immediate severe harm in the actual scope; distinguish a synthetic example from an observed live incident.

Give findings stable identifiers and retain them through handoff, developer response and re-review; link newly discovered findings separately. Use ordinary prose or the project format, without a mandatory schema. Account for each assigned requirement using the [scope and criteria guidance](intent_context.md#compare-and-report), and state what remains unassessed.

### Consolidating findings

Combine reports of the same underlying failure while preserving relevant consequences and verification obligations. Different severities or requirement labels do not alone create separate defects. A shared correction alone does not make distinct faulty mechanisms or independently affected paths duplicates. Preserve original evidence and explain material disagreement; do not hide a serious supported finding through voting.

## Specialist return

Return findings, inspected scope and important limitations to the lead in a concise message. Prefer per-criterion and per-variant outcomes; omit unrequested aggregate counts. If the user requests aggregates, verify them against the actual dispositions. Opening summaries must preserve mixed met, partial and not-assessed outcomes rather than override detailed limitations with an overall pass. Report useful partial findings even when another question is blocked. When another specialty is required, name the owner role and precise unassessed evidence or question in the request to the lead; a referral does not establish completed coverage. Distinguish a source defect from a missing input, denied tool or unperformed check. Do not invent a successful inspection, alter sources or take over the final user response.

## Developer handoff and response contract

Give the developer the retained findings, reviewed source, suggested corrections, verification needs and unresolved decisions. Before handoff, account for each original finding—including fixed, partial, deferred and blocked items—by retaining its correction, material tradeoffs and verification obligations in concise text or explicit stable per-finding references; explain source- or criterion-based revisions and account for omissions. The optional [handoff template](templates/review-handoff.md) can be included in the review itself.

The developer responds per finding with what changed or why it remains disputed, deferred or blocked; relevant files/revision; actual checks and results; and remaining risks or decisions. One shared fix can reference several findings. Partial fixes and omitted responses remain visible. Do not demand commits or pre-fix execution logs that do not exist; use the working tree and explain evidence limits. See the optional [response template](templates/developer-response.md).

Re-review the actual changed source against the original failure and relevant valid paths. Apply the [independence policy](review_policy.md#evidence-and-judgment). Confirm source and governing-requirement freshness, inspect affected changes and new risks, and report fixed, partially fixed, unresolved or withdrawn findings under their original identifiers with reasons. Qualify obsolete evidence rather than using it to close current work. A developer's claim or passing test alone does not close a finding. Final coverage can remain incomplete while supported findings and corrections are reported.
