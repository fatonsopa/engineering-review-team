# Architecture review research references

Consult this record when verifying a source, checking a version-dependent claim or maintaining the reviewer. Do not load it automatically for routine reviews. The technical standard owns the controls; these references do not independently create project obligations.

## Domains references

[SEI architecture evaluation](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/) supports scenario-based tradeoff analysis; [arc42 quality scenarios](https://docs.arc42.org/section-10/) explains operational and change scenarios. [Microsoft architecture styles](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/) illustrates context-dependent constraints and costs. These sources inform package defaults; they do not create project requirements. Select applicable source versions through the team [project intent guidance](../intent_context.md).

## Control-to-source mapping

The entries below preserve the source associations and qualifications used when authoring the controls. They are research evidence, not additional review instructions.

- **ARCH-01 — Quality scenarios and architectural intent:** Owner/contributors; basis: Architecture owns scenario analysis; the lead resolves intent, affected specialists supply evidence. [S1], [S2]; scenario selection and review obligations are package defaults.
- **ARCH-02 — Modular boundaries and rule ownership:** Owner/contributors; basis: Architecture owns system responsibility; Code checks local implementation and Database supplies write-boundary evidence. [S3], [S4]; cross-consumer comparison is a package method.
- **ARCH-03 — Dependency direction and coupling:** Owner/contributors; basis: Architecture owns dependency analysis; Code, Testing and DevOps contribute local, isolation and startup evidence. [S3], [S4], [S10]; graph classification and consequence test are package methods.
- **ARCH-04 — Pattern applicability and abstraction cost:** Owner/contributors; basis: Architecture owns structural tradeoffs; Code and affected specialists contribute concrete costs. [S3], [S5], [S6]. Requiring a focused comparison is a package default, not a mandate for a separate Decision Record (DR).
- **ARCH-05 — Owned integration contracts:** Owner/contributors; basis: Architecture owns boundary semantics; Code checks adapters, Database storage guarantees, Security trust boundaries and DevOps provider configuration. [S4], [S7], [S9]; binding and ownership inspection are package methods.
- **ARCH-06 — Runtime and deployment lifecycle:** Owner/contributors; basis: Architecture owns interactions and state lifetimes; DevOps supplies platform/release evidence, Code worker behavior and Database durability. [S2], [S8]; lifecycle trace is a package method.
- **ARCH-07 — End-to-end failure isolation:** Owner/contributors; basis: Architecture owns failure propagation; Code retry/cancellation correctness, Performance capacity and DevOps operational recovery contribute. [S9], [S10]. Numeric budgets remain project parameters.
- **ARCH-08 — Atomicity and recoverable multi-component effects:** Owner/contributors; basis: Architecture owns cross-component invariants; Code orchestration, Database transactions and DevOps recovery contribute. [S9], [S11], [S12]; the fault-window method below is retained package practice.
- **ARCH-09 — Asynchronous consistency and derived state:** Owner/contributors; basis: Architecture owns consistency across consumers; Code delivery logic, Database persistent semantics, Performance cache costs and Compliance established lifecycle obligations contribute. [S6], [S11]; replay/lifecycle comparison is a package extension.
- **ARCH-10 — Tenancy model and context boundaries:** Owner/contributors; basis: Architecture owns the model and cross-component context; Security, Code, Database and DevOps supply enforcement and placement evidence. [S13], [S14].
- **ARCH-11 — Tenant lifecycle and data disposition:** Owner/contributors; basis: Architecture owns lifecycle coordination; Code, Security, Database, DevOps and Compliance contribute their affected controls. [S15], [S16]; complete-copy tracing and interruption analysis are package methods.
- **ARCH-12 — Entitlement ownership and propagation:** Owner/contributors; basis: Architecture owns authority/propagation design; Code implementation, Security access enforcement and Performance cache behavior contribute. [S17]; cross-consumer authority and failure analysis are package defaults.
- **ARCH-13 — Compatibility and migration:** Owner/contributors; basis: Architecture owns system transition; Code API/message behavior, Database migration integrity and DevOps rollout/recovery contribute. [S7], [S18].
- **ARCH-14 — Workload scaling and capacity constraints:** Owner/contributors; basis: Architecture owns structural limits and scaling tradeoffs; Performance owns measurement, Database store bottlenecks and DevOps provisioning limits. [S19], [S10], [S20]; the capacity-claim check is a package method.
- **ARCH-15 — Partition and failure-domain tradeoffs:** Owner/contributors; basis: Architecture owns common dependencies and system tradeoffs; Database, DevOps, Performance and Security contribute actual storage, recovery, capacity and boundary evidence. [S10], [S20], [S21].
