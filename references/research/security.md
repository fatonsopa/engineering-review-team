# Security review research references

Consult this record when verifying a source, checking a version-dependent claim or maintaining the reviewer. Do not load it automatically for routine reviews. The technical standard owns the controls; these references do not independently create project obligations.

## Domains references

[OWASP secure code review guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html) supports change-aware, contextual flow analysis. [OWASP threat modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) supports selecting threats from system boundaries and actors. [ASVS](https://asvs.owasp.org/) supplies versioned web-security requirements. These sources inform the package method; the [project intent guidance](../intent_context.md) and effective supplied requirements and decision evidence determine their actual application.

## Control-to-source mapping

The entries below preserve the source associations and qualifications used when authoring the controls. They are research evidence, not additional review instructions.

- **SEC-01 — Assets, threats and trust boundaries:** An export worker's privileged database identity does not authorize tenant-local IDs submitted through its public API. Trace the originating actor, tenant and object through enqueue, execution and download to the access check. Security owns threat applicability; Architecture supplies topology and Compliance established obligations. Reconstruction is not an approved Threat Model (TM). S2 supports the method; control selection and evidence requirements are package design.
- **SEC-02 — Authentication, enrollment and recovery:** Recovery must not accept an unverified replacement email and issue a full session for an account requiring a second factor. Prove the established account relationship, apply recorded recovery assurance and grant only authorized permissions. Security owns assurance and abuse; Code supplies implementation and Design usability. Do not invent an RBAC model, identity provider or fixed password/session lifetime. S3 and selected ASVS references.
- **SEC-03 — Authorization, tenant isolation and delegated access:** A cache keyed only by `item_id` can return tenant A's bytes to tenant B before a tenant-scoped query runs. Include verified tenant and other required authorization dimensions in the lookup; the returned object must still satisfy action permission. Opaque IDs, UI restrictions and authentication alone are insufficient. Security owns access judgment; Database supplies storage enforcement and Architecture context propagation. RBAC, ABAC and relationship rules depend on the project. S4; tenant-cache and export cases remain in scope.
- **SEC-04 — Sessions, cookies and revocation:** Deleting a browser cookie does not reject a copied credential. An immediate-logout contract needs enforcement across relevant consumers through server state or the chosen validation mechanism. Security owns session trust; Code implements transitions. Choose supported lifetimes with their usability/recovery costs; do not prescribe JWT or cookies where another mechanism fits. S5.
- **SEC-05 — Federation, OAuth and token validation:** An API must not accept an ID token issued for another client merely because its JWT signature verifies. Enforce token class, issuer, audience, time and claims before separate resource authorization. Security owns protocol trust; Code and DevOps supply library/provider settings. S6, S7.
- **SEC-06 — Input meaning, canonicalization and object construction:** An object accepted as a username can become a query operator. Require the intended bounded scalar, construct an application-owned query and enforce access separately. Security owns hostile-input consequences; Code contributes type/contract correctness. Do not strip ordinary punctuation or impose one normalization rule on every language/name field. S8, S9; prototype concerns also map to ASVS.
- **SEC-07 — Interpreter and query injection:** Interpolating user values into SQL before `execute`, or into template source, can cross the instruction boundary. Bind SQL values with trusted structural choices; pass text into fixed templates with appropriate output protection. See the stack examples. Validation, an ORM name or shell escaping alone does not prove safety. Security owns injection; Database supplies stored-language details and Code API use. S9–S12 and selected ASVS references.
- **SEC-08 — Browser output and cross-site scripting:** `element.innerHTML = comment` interprets a comment as markup. An ordinary text element can use `textContent`; permitted HTML needs configured sanitization. `textContent` on a script element is not safe text display. Security owns script-execution risk; Code and Design supply framework/UI behavior. S13.
- **SEC-09 — Browser origins, CSRF and cross-context access:** An ordinary cross-origin form must not mutate a cookie-authenticated setting without effective anti-forgery enforcement. Validate context before mutation and permit only intended integrations. Security owns origin trust. CORS is not API authorization; `SameSite` alone does not universally prevent CSRF. Headers depend on the feature/browser contract. S14 and related ASVS controls.
- **SEC-10 — Server-side requests, redirects and egress:** A once-checked webhook URL can redirect to a restricted internal endpoint while carrying authorization headers. Enforce destination/credential policy at each connection/redirect, with appropriate egress restrictions. Security owns SSRF and credential exposure; DevOps supplies network evidence. Hostname substrings or initial DNS checks alone are insufficient. Unknown reachability limits impact claims. S15.
- **SEC-11 — Parsers, deserialization and XML:** Base64 does not make uploads safe for `pickle.loads`. A bounded data-only format with schema validation avoids arbitrary object reconstruction for that input. Likewise, `safe_load` is insufficient if custom constructors restore executable behavior. Security owns parser abuse; Code supplies implementation. S16–S18.
- **SEC-12 — Files, paths, uploads and archives:** Joining an archive entry to a destination does not constrain the actual write. Enforce entry/link rules there, prevent unauthorized overwrite and process permitted content under bounded privileges. Security owns file abuse; Code and DevOps supply filesystem/runtime semantics. Extensions/MIME alone are insufficient; antivirus does not establish harmlessness. S19.
- **SEC-13 — API, proxy and message boundaries:** A caller-supplied `X-User-ID` forwarded unchanged is not authenticated identity. Accept trusted metadata only from a verified intermediary, remove untrusted copies and enforce application authorization. Security owns boundary bypass; DevOps supplies deployment paths and Code protocol use. REST guidance does not define every RPC/streaming protocol; read its actual specification. S20 and versioned ASVS API references.
- **SEC-14 — Secrets and service credentials:** CI substitution can put a backend secret into a public frontend bundle. Send browsers only intended public configuration; provision backend credentials with controlled, narrow authority. Security owns misuse; DevOps supplies provisioning and Database permissions. Do not read live secrets. A vault or environment variable alone does not prove secure access. S21.
- **SEC-15 — Cryptography, key use and password storage:** Unsalted fast hashes expose passwords to efficient guessing. Reusing a nonce with the same key after a deployment-counter reset is a separate defect when the algorithm requires nonce uniqueness. Use suitable password-hash salts/costs and preserve algorithm-specific nonce requirements across restarts/replicas. Security owns judgment; Code and DevOps supply implementation/custody facts. Do not prescribe custom crypto, arbitrary algorithms or automatic FIPS/post-quantum obligations. S22, S23.
- **SEC-16 — Transport and peer authentication:** Disabling certificate verification can let an untrusted endpoint impersonate a payment provider under the modeled threat. Validate against established trust and reject mismatched/untrusted peers without insecure retry. Security owns peer trust; DevOps supplies termination/network evidence. Private networks alone do not authenticate peers; do not require a universal service mesh or public CA for an intentionally private trust domain. S24.
- **SEC-17 — Sensitive data and lifecycle exposure:** A public-profile serializer must not return private recovery fields from the account object. Select permitted fields, preserve recipient boundaries in caches and apply established lifecycle rules to other copies. Security owns exposure; Compliance establishes obligations, Database persistence and Architecture lifecycle coordination. Encryption at rest does not prevent an authorized application disclosing plaintext. S4, S22 and selected ASVS data controls.
- **SEC-18 — Dependencies and supply-chain exposure:** Executing an untrusted mutable download with release credentials violates a boundary limited to an established publisher. Verify publisher/version through a trusted mechanism, scope build authority and assess applicable advisories. Security owns compromise/exposure judgment; DevOps contributes provenance and Compliance licenses. An old version, CVE label, lockfile or signature alone proves neither exploitability nor trust. S25.
- **SEC-19 — Configuration and privileged attack surface:** An interactive production debugger reachable by ordinary users can grant privileged execution. Exclude it from production or enforce the actual restricted administrative boundary. Security owns unauthorized exposure; DevOps owns the full infrastructure/release assessment. No universal container platform, private-only backend or network product is required. S20, S25 and mapped ASVS controls.
- **SEC-20 — Resource exhaustion and denial of service:** An archive can pass an upload limit yet exhaust storage during expansion. Enforce expanded-byte/count/time budgets while extracting, clean partial state and bound concurrent work under actual tenant/shared policy. Security owns adversarial availability; Performance supplies measurements, DevOps volumetric/network mitigation and Architecture isolation. Do not invent requests-per-second targets, mandate universal CAPTCHA or run DoS probes. S26; input/file sources support specific limits.
- **SEC-21 — Business abuse, concurrency and replay:** Two requests can both grant an unused credit before either marks it used. Reserve/consume atomically under the verified store contract and reconcile permitted retries. Security owns abuse; Code contributes local correctness and Database/Architecture atomicity. Lost payment notification alone does not prove duplicate payment; use Architecture's fault-window method for that claim. S27.
- **SEC-22 — Security events, errors and failed controls:** Converting authorization-service exceptions to `allowed = true` while logging bearer tokens compounds access and disclosure failures. Follow the supported secure failure path, retain redacted attributable events and return nonsensitive errors. Security owns event meaning; DevOps supplies delivery/alert response and Compliance audit obligations. Do not reproduce secrets or infer nonrepudiation from ordinary logs. S28.
- **SEC-23 — AI, retrieval and tool authority:** A retrieved document must not make a tool send another tenant's records to an external URL. Retrieval/execution must independently enforce actor, tenant and recipient boundaries, with bounded repeated work. Security owns hostile-instruction/authority abuse; Code/Architecture supply execution details, DevOps deployment and Compliance data use. One refusal does not prove prompt-injection resistance. No new host or exploitation authority follows. S29, S30.
- **SEC-24 — Native memory and unsafe runtime boundaries:** An image wrapper can allocate using overflowed width-times-height, then copy full decoded pixels into the smaller buffer. Checked arithmetic/bounds must establish allocation-versus-copy sizes with correct ownership and failure cleanup. Security owns hostile impact; Code contributes language correctness and Testing evidence. A managed language does not make native extensions safe; sanitizer success does not cover all inputs. S31 and ASVS memory controls.
